# Design

## Context

See proposal.md for why. The code this design works with:

- **Version.** `vite.config.ts` injects `package.json`'s `version` as `__APP_VERSION__`, and `SidebarContent` shows `v{__APP_VERSION__}`. Nothing else reads the version.
- **Not-found page.** `src/app/NotFoundPage.tsx` is the `*` route inside `RequireAuth` and `AppShell`, so only signed-in users reach it. It shows a heading, a line and a link. `public/art/` is generated by `npm run build-art` from the owner's archives and holds a manifest; files placed there by hand would not be in it. `sharp` is already a dev dependency (used by `scripts/lib/artWrite.ts`). `tsconfig.app.json` includes `vite/client`, so importing a `.webp` file gives its URL.
- **Roll records.** Every roll is a `diceRolls/{rollId}` document. A hidden roll also has `dmRolls/{rollId}`, written in the same batch. The rules end both with `allow update, delete: if false`. The channel listens to the newest 50 (`recentRollsQuery`), and the DM also to `recentDmRollsQuery`. `DicePage` keeps the strip in local state (`strip ?? newestWithContent`), so a roll played this session would stay in the strip after its record is gone.
- **Combat does not depend on roll records after the write.** A character combatant's `roll` keeps `rollId`, `die` and `modifier`; an NPC's `dmCombatants` doc keeps the same. The rules check `rollId` only with `createdNow(...)` at the moment of the roll (`firestore.rules`, around line 2724). Nothing reads `diceRolls` by `rollId` afterwards.
- **Table change records.** `tableChanges/{id}` holds `{by, at, setting: 'playerDraw', before, after}` and is validated with a single Zod object (`src/features/table/schema.ts`). Only the activity log reads it (`src/features/activity-log/api.ts`, without a player filter), turning each into a `tableSetting` event whose text is built in `eventText.ts`. The converter throws `InvalidDataError` on a document that does not match the schema.
- **Ayarlar.** `SettingsPage` ends with a static "Veri / Yedek" section saying backup is coming soon. `useIsDm()` gives the role. `AccessSection` already has a DM confirmation flow built on `components/ui/Dialog`.

## Goals / Non-Goals

**Goals:**
- Delete every roll record, public and DM-only, from the DM's client, with no server code.
- Record the reset in the existing log pipeline without a new collection or a new log query.
- Keep the not-found picture out of the `build-art` manifest and serve it with the hashed, immutable caching that Vite assets get.

**Non-Goals:**
- Deleting only some rolls (by date, by player, only hidden ones).
- Undoing a reset, or exporting the rolls before deleting them. The "Veri / Yedek" backup stays a later change.
- Tying the deletes to the record on the server. A reset can need many batches, so the rules cannot see them as one request.
- Git tags or release notes for 1.0.0.

## Decisions

### D1. The DM's client deletes the rolls in batches

`resetDiceChannel(db, { by })` in `src/features/dice/api.ts`:

1. Reads every ID in `diceRolls` and in `dmRolls` from the server (`getDocsFromServer`, IDs only matter). Offline, this fails, and the screen shows the connection message.
2. Counts the `diceRolls` documents as the number of rolls (hidden rolls count once).
3. Writes the first batch: the `tableChanges` record (D2) plus as many deletes as fit, then the remaining deletes in batches of at most 500 writes, in order, awaiting each.

Deleting `dmRolls` from their own listing rather than from the hidden public records also clears any orphaned DM-only content.

*Alternatives:* a callable Cloud Function or the Admin SDK script would delete atomically and server-side, but the project has no Functions, and the DM needs the button in the app. A "reset marker" on the table (the channel only shows rolls after `resetAt`) would be one atomic write, but the records would stay forever and the DM-only content would still be readable; the owner asked for the data to be cleared.

### D2. The reset is a `tableChanges` record with `setting: 'diceReset'`

The record is `{by, at, setting: 'diceReset', rolls}`, where `rolls` is the whole number of rolls deleted. `tableChangeSchema` becomes a discriminated union on `setting`: the existing `playerDraw` shape, and the `diceReset` shape. `TABLE_SETTINGS` gains `diceReset`. The activity log keeps its single `tableChanges` query. `eventText.ts` switches on `change.setting`: the existing text for `playerDraw`, and `zar kanalını sıfırladı: <n> atış.` for `diceReset`.

The rules for `tableChanges` gain a second branch, alongside the existing `validTableChange()`: keys exactly `by, at, setting, rolls`, `by` the signed-in user, `at` the request time, `setting == 'diceReset'`, `rolls` an int `>= 0`, and `isDm()`. It is not tied to the deletes (see Non-Goals). The record goes in the first batch, so a reset that fails at its first write leaves neither record nor deletes.

*Alternative:* a new `diceResets` collection. It would need its own log query, its own entry in the log's paging bookkeeping (`events.ts` checks each source against the limit) and its own rules block, for one rare event. Reusing `tableChanges` costs a union in one schema.

### D3. The rules let the DM delete roll records

`diceRolls` and `dmRolls` change from `allow update, delete: if false` to `allow update: if false; allow delete: if isDm();`. A player's delete stays denied. Creating stays exactly as it is.

### D4. The strip forgets a roll that no longer exists

In `DicePage`, the local `strip` state is used only while its roll is still in the list of rolls; otherwise the page falls back to `newestWithContent`, which is `null` after a reset, so the strip is empty. The menu's unseen count needs no change: it is computed from the rolls in the window, so deleted rolls stop counting.

### D5. The reset in the Ayarlar screen

`SettingsPage`'s "Veri / Yedek" section becomes a component. For the DM it shows a "Zar kanalı" block: a line on what a reset deletes and keeps, and a danger-styled `Button` "Zar kanalını sıfırla". The button is disabled when the DM's channel listener holds no rolls. Selecting it counts the rolls on the server (`getCountFromServer`, through `countRolls` in the dice actions), then opens a `Dialog` that names the count and, when `combat/main` is not idle, adds the line that the initiative order stays. "Sıfırla" runs D1, with the busy state on the button and Turkish error texts (connection needed, or failed part way: "Bazı atışlar silinemedi; tekrar dene"). After success the dialog closes. Players see only the backup note.

The count in the dialog comes from the server, not from the channel's listener, which holds only the newest 50 rolls. The count stored in the record is the one read in D1 step 2, which is what was actually deleted. `DiceResetIncompleteError` and the Turkish failure texts live in `src/features/dice/errors.ts`, so the screen does not import the Firestore module.

### D6. The manticore picture is a bundled Vite asset

Convert `~/Downloads/mahcup_ama_tehlikeli_mantikor.png` once with `sharp` to a WebP 1200 px wide (quality around 80), saved as `src/app/notFoundManticore.webp`, and commit only the WebP. `NotFoundPage` is only the picture, centered in the page (the section takes the rest of the shell's `main` with `flex-1`), `w-full max-w-2xl h-auto` with rounded corners, and one muted line under it, the `h1` "Sayfa bulunamadı". It has `width`/`height` attributes from the file to avoid layout shift, `alt="Mahcup ama tehlikeli bir mantikor"`, and no phone hiding (it is not a `Mascot`). The owner asked for nothing else on the page, so the old "Oyuncu elleri ekranına dön" link is gone; the menu stays for leaving. If the image fails to load, the `<img>` hides itself, and the line stays.

*Alternative:* adding it to `build-art` as a mascot. `build-art` needs the owner's archives and alias table to run, and `Mascot` hides itself on phones, which the page must not do.

### D7. Version 1.0.0

`npm version 1.0.0 --no-git-tag-version` updates `package.json` and both version fields of `package-lock.json`. Nothing else changes.

## Risks / Trade-offs

- **A reset is not atomic.** If the connection drops between batches, part of the rolls are deleted and the record already says how many were found. → The dialog shows the failure. Running the reset again deletes the rest and writes a second record with the remaining count. The log shows two events, which is accurate.
- **A roll made during a reset can survive it.** It was created after step 1's read. → Acceptable for a rare DM action at a table of friends. The spec says so.
- **Deletes cannot be undone.** → The confirmation names the count. Point-in-time recovery on the live project (enabled at go-live) is the emergency way back.
- **An old client and a new record.** A browser tab still running the pre-1.0.0 build would throw `InvalidDataError` on the log screen when it reads a `diceReset` record. → Hosting serves `index.html` with `no-cache`, so a reload fixes it. The table updates at the same time.
- **The rules' expression budget.** The new `tableChanges` branch and the `delete` rules are small and do not touch the roll validation path, so the 1000-expression limit is not at risk.

## Migration Plan

No data migration: existing records stay valid under the new schema. Deploying rules and hosting together through CI, as usual. Rollback: redeploy the previous build and rules. Existing `diceReset` records would then fail the old schema in the log until the rollback is undone, so roll back only before the first reset, or remove those records by hand.
