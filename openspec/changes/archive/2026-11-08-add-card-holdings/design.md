# Design

## Context

See `proposal.md` for the motivation, and `specs/` for the behavior contracts (`card-holdings`, plus the deltas to `card-library` and `user-profiles`).

**Current state**
- **Cards.** `cards/{cardId}` holds the definitions, written only by `npm run import-cards` with merge writes of the definition fields and `retired`. `firestore.rules` gives read access to signed-in users and has `allow write: if false`.
- **Cards in the app.** `CardsProvider` subscribes to `where('retired', '==', false)`. `useDeckCards()` splits the cards into the Legend and Cursed decks, and `CardBrowser` renders them.
- **Profiles.** `UsersProvider` shares the profiles. `useIsDm()` and `<DmOnly>` exist, but no rule checks the role yet: there is no `isDm()` helper.
- **Screens.** `HandsPage` is a placeholder at `/hands`. The "Oyuncular" list (`PlayerList`) shows names without links. `SidebarContent` is shared by the sidebar and the mobile menu.
- **Target model.** The model agreed in `add-user-roles` ("Target data model") fixes the shape of `userCards` and `cards.holder`, and the action table of who may do what.

**Decisions from the exploration with the owner**
- **No migration.** "Drawn?" is ignored.
- **The table's state is entered last,** by the DM with the normal give action. The target model's `givenVia: 'initial'` is therefore dropped.
- **LP stays with pack-opening.**
- **Player notes wait** for a later change.

## Goals / Non-Goals

**Goals:**
- **One source of truth for "in the pool".** A normal card's `holder` decides it. The rules keep `holder` and the holdings consistent, even against a hand-crafted client.
- **History from day one.** Holdings are closed, never deleted, so the later log and history screens have data.
- **Readiness for pack-opening.** Packs and draws add `givenVia: 'pack' | 'draw'` and a `drawId` to the same records and the same give transaction.

**Non-Goals:**
- **No history screen.** Closed holdings are stored but not shown. The İşlem Logu comes with pack-opening.
- **No undo.** A mistake is corrected with the opposite action: give the card again, or transfer it back.
- **No drag and drop.**
- **No offline card movements.** See Risks.

## Decisions

### D1. Holding document

```
userCards/{holdingId}       ID generated by the client, so the same transaction can point the card's holder at it
  cardId          string               the card's document ID
  cardName        string               the name when given, so history reads well after a rename
  cardKind        'normal' | 'blessed' | 'cursed'   copied from the card; the rules check it against the card
  uid             string               the holder; must have a profile
  givenAt         timestamp            = request.time
  givenBy         string               uid of the giver
  givenVia        'dm' | 'transfer'    later also 'pack' | 'draw' (pack-opening)
  transferredFrom string | null        for 'transfer': the closed holding this one continues
  active          boolean
  note            string (0-1000)
  costOverride    string (1-10) | null
  returnedAt      timestamp | null     null = open
  returnedBy      string | null
  returnReason    'used' | 'discarded' | 'transferred' | null
  usedOn          string (1-100) | null   "on which character", only for 'used'
  transferredTo   string | null        for 'transferred': the new holding
```

**Changes to the target model:**
- `initial` is dropped (see Context).
- `drawId` arrives with pack-opening.
- `cardKind`, `transferredFrom`, and `transferredTo` are new. They let the rules check a transfer from both sides without querying, and they let a later history screen follow a card from hand to hand.

**The hand order** is `givenAt`, ascending. A transfer opens a new holding, so the card goes to the end of the receiver's hand, as in the legacy app. A pending server timestamp reads as `null` in the local snapshot, and such a holding sorts last.

### D2. The card's holder

The card schema gets `holder: { uid, userCardId } | null`. It has a zod default of `null`, because no stored card has the field yet.
- **Kinds.** Normal cards use the field. On Blessed and Cursed cards it is always `null`.
- **The import never writes it** (merge writes, see `add-card-library`), so a re-import keeps the pool state.
- **Extra copies.** The holder points at exactly one holding. An extra copy (spec: "DM extra copy of a held card") is a holding whose card points elsewhere. When the holder's holding closes, the card returns to the pool even if an extra copy is still in a hand. That is the target model's rule, and the DM chose to make the copy. The library still lists that copy's holder by name, from the holdings (D6).

### D3. Movements are client transactions

`src/features/hands/api.ts` runs each movement as one Firestore transaction. Each transaction re-reads the card and the holding inside it:

| Action | Reads | Writes |
| --- | --- | --- |
| give (pool card) | card | holding created; `card.holder = { uid, holdingId }` |
| give (extra copy, confirmed) | card | holding created |
| give (Blessed or Cursed) | card | holding created |
| use / discard | holding, card | holding closed (`returnedAt`, `returnedBy`, `returnReason`, `usedOn`); `card.holder = null` if it pointed at this holding |
| transfer | holding, card | old holding closed as `transferred` with `transferredTo`; new holding created with `transferredFrom`, the same `note`, `costOverride` and `active`; `card.holder` moved if it pointed at the old holding |

**Plain updates.** Notes, `active`, and `costOverride` are single-field `updateDoc` calls with no transaction. They work offline, and the subscription shows them at once.

**Failures** the UI handles, with Turkish messages:
- The card was taken between showing the dialog and confirming. The transaction re-reads `holder`, and the UI offers the extra-copy confirmation.
- The holding was already closed, for example used on another device.
- No connection: transactions need the server.
- Permission denied.

**Alternative: a Cloud Function.** It would need Functions in the stack and a paid plan. The rules (D4) already make a hand-crafted client harmless.

### D4. Rules: both sides check each other with `getAfter`

A card movement writes two or three documents in one transaction. Each document's rule checks the other side's final state with `getAfter`/`existsAfter`. So no write can leave `holder` and the holdings disagreeing, even when written outside the app.

```
function isDm() {
  return isSignedIn()
    && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'dm';
}

match /userCards/{holdingId} {
  allow read: if isSignedIn();
  allow create: if isDm() && validNewHolding(holdingId);          // givenVia dm or transfer
  allow update: if resource.data.returnedAt == null && (
       onlyChanges(['note']) && validNote() && (isDm() || isHolder())
    || onlyChanges(['active']) && isDm()
    || onlyChanges(['costOverride']) && validCost() && isDm()
    || closesAs('used') && (isDm() || isHolder()) && holderReleased()
    || closesAs('discarded') && isDm() && holderReleased()
    || closesAsTransferred() && isDm() && holderMovedToNewHolding()
  );
  allow delete: if false;
}

match /cards/{cardId} {
  allow read: if isSignedIn();
  allow update: if isSignedIn()
    && onlyChanges(['holder'])
    && resource.data.kind == 'normal'
    && (takenFromPool() || releasedByClosedHolding() || movedByTransfer());
  allow create, delete: if false;
}
```

**Holding create, `validNewHolding`:**
- exact keys, with the types and limits of D1
- `givenAt == request.time` and `givenBy == request.auth.uid`
- open: every `returned*` field is `null`
- the receiver has a profile: `exists(users/$(uid))`
- the card exists, and its `kind` equals `cardKind`
- a `dm` give needs a card that is not retired
- **for a normal card,** the card's final holder must match one of:
  - from the pool: before `null`, after `{ uid, holdingId }`
  - an extra copy: before equals after, and not `null`
  - a transfer: before `{ …, transferredFrom }`, after `{ uid, holdingId }`
- **a `transfer`** also needs the holding named in `transferredFrom` to be closed as `transferred`, with `transferredTo == holdingId`, after the write

**Card update.** Each case needs a matching holding in its final state:
- **`takenFromPool`:** the new holding exists, is open, and has the same card and uid. Before the write the holding did not exist.
- **`releasedByClosedHolding`:** the holding the old holder points at is closed as `used` or `discarded`.
- **`movedByTransfer`:** the old holding is closed as `transferred`, and its `transferredTo` is the new holder's holding.

**Closing a holding.** If the card is normal and its holder points at this holding, the card's final holder must be `null` (use, discard) or the transfer target (transfer). Otherwise the card must not change.

**Budget.** Firestore allows 20 document reads per multi-document request, and repeated reads of the same document are cached. A transfer, the largest case, reads the profile, the card twice, and both holdings: well within the limit.

**`resource.data.get('holder', null)`** treats imported cards without the field as `null`.

**Tests** (`tests/firestore.rules.emulator.test.ts`, a `userCards` block and an extended `cards` block):
- every allowed path for each role
- every denied path, including:
  - forged holders, and a holder with no holding
  - a holding created without setting the holder
  - a player closing someone else's card
  - a player discarding or transferring
  - a change to a closed holding
  - changing the card text together with the holder
  - a delete
  - a holding for a user ID without a profile

### D5. The "Oyuncu elleri" screen

**Routes.**
- `/hands` stays the menu entry and redirects, with `replace`:
  - a player goes to their own hand, `/hands/<uid>`
  - the DM goes to the first non-DM profile in the list, or to their own hand
- `/hands/:uid` is a route under `AppShell`, without its own `SCREENS` entry. The menu's `NavLink` for `/hands` stays marked on it.
- The "Oyuncular" names link to `/hands/<uid>`, and the shown user gets `aria-current`.

**Layout:**

```
[PageHeader "Ayla — Kart Eli"]                         [+ Kart ver]  (DmOnly)
[ELDEKİ KART 7] [AKTİF EFEKT 2] [FARKLI SET 3] [CURSED KART 1]
[Aktif efektler: name + visible text ...]   [Setler: Kesqerian Nights 3 ...]
[▦ Kartlar] [☷ Liste]
grid of hand cards (CardFace + markers)  |  table: # Kart Set Cost Rarity Mechanic Metin Durum
```

**Hand cards** reuse `CardFace`. It gets optional props for:
- the hand's cost, with a lower or higher mark (`green` for lower, `cursed` for higher, after the legacy badge)
- an "Aktif" mark, in the frame color
- a note mark (✎)
- an "Ek kopya" mark for extra copies

Each card is a button that opens its details.

**Details dialog.** It is a native `<dialog>` (`showModal`), on every width. It shows:
- the card face
- the note field: the holder and the DM can edit it; it is saved on blur
- the cost override field, DM only
- "Kullan", with an optional "Hangi karakter üzerinde?" field and its own confirm button
- for the DM: "● Aktif et" / "✓ Aktifliği kaldır", "At" with an inline confirmation, and "Başkasına ver" with a player picker and confirmation

Controls the user may not use are not shown, but the rules still decide. Confirmations are steps inside the dialog, never `window.confirm`.

**Alternative: the legacy side panel.** It was rejected for now. It needs two layouts, side panel and stacked, and on phones it ends up below a long hand. The dialog works the same on every width.

**"+ Kart ver" dialog (DM).**
- It has the library search (`cardHaystack`) over every active card of both decks.
- Each result shows its status: "Havuzda", "Elde: Bora", or the kind.
- Choosing a held normal card shows "Bora'nın elinde. Ek kopya verilsin mi?" before anything is written.
- The dialog stays open after a give, so the DM can give several cards in a row. That is the main use when entering the table's state at the end.

### D6. Holdings in the app: one app-wide subscription

`HoldingsProvider` follows the `UsersProvider` and `CardsProvider` pattern:
- It is mounted in `App.tsx` under `CardsProvider`.
- It subscribes to `where('returnedAt', '==', null)` while signed in. That is one filter, so no composite index is needed.
- It exposes `useOpenHoldings()`, plus derived helpers:
  - `holdingsOf(uid)`, sorted by `givenAt`
  - `holdersOf(cardId)`
- `TestHoldingsProvider` and a `holdings` option on `renderApp` keep the unit tests off Firebase.

**Cards.** `CardsProvider` now subscribes to all cards, retired ones included: the same about 745 documents. It exposes:
- `useCards()`: still the active cards only, so the library behaves as before
- `useCardsById()`: a map that includes retired cards, so a hand can show a held card that was retired (spec: "Retired cards stay in hands")

**Library status.** `CardBrowser` gets a `status` input computed from three sources: the cards (holder), the open holdings (names of every copy), and the profiles. It drives:
- **the Durum column:** "Havuzda", "Elde: Ayla, Bora", or "Havuzda · Elde: Ayla" for Blessed
- **an "Elde" mark** on the faces of held normal cards
- **the "Yalnızca havuzdakiler" checkbox,** on the Legend deck only
- **the counts:** "Havuzda N · Ellerde M". In the pool: normal cards without a holder, plus Blessed cards. In hands: open holdings of Legend cards.

The Cursed Deck shows its holders in its own Durum column, and on its faces.

### D7. Where the code lives

```
src/features/hands/
  schema.ts, api.ts               holding schema and converter; give, close, transfer, update
  holdingsContext.ts              context, useOpenHoldings, holdingsOf, holdersOf
  HoldingsProvider.tsx
  HandsPage.tsx                   /hands redirect and /hands/:uid
  HandSummary.tsx, HandView.tsx, HandTable.tsx, HoldingDialog.tsx, GiveCardDialog.tsx
  errors.ts                       Turkish messages for the transaction failures
src/features/cards/               holder in schema, useCardsById, pool status in CardBrowser and CardFace
src/features/users/PlayerList.tsx names become NavLinks
src/test/                         TestHoldingsProvider, holding fixtures
```

`features/hands` uses `features/cards` and `features/users` the way `users` uses `auth`: through their exported hooks and components.

## Risks / Trade-offs

- **[Risk] The rules are the most complex part of the app so far.** Mitigation:
  - every movement checks the other side with `getAfter`
  - helpers have names that match the spec words
  - D4 lists a rules test for each allowed and each denied path
  - emulator tests run the real transactions under the real rules
- **[Trade-off] Card movements need a connection.** Transactions fail offline. The DM sees "Bağlantı yok", and nothing half-done is queued. Notes, `active`, and `costOverride` still work offline.
- **[Trade-off] A DM extra copy does not keep its card out of the pool** once the original holder's holding closes (D2). This is accepted from the target model. The library still names everyone holding a copy.
- **[Trade-off] Every role-checked write reads the user's profile once** (`isDm()`), as accepted in `add-user-roles`.
- **[Risk] Two devices give the same pool card.** Mitigation: the transaction re-reads `holder`. The rules deny a holder that is not `null` before the write. The loser sees the extra-copy question.
- **[Risk] A retired card stays held** and its definition is no longer listed. Mitigation: `useCardsById()` includes retired cards, so the hand still shows it until the holding closes.

## Migration Plan

- **No data migration.** Stored cards have no `holder` field, and the schema default and the rules treat it as `null`. No holdings exist yet.
- **Deploying the rules together with the app** keeps old clients harmless: an older build never writes cards or holdings.
- **Rollback:** revert the change. The holdings stay stored but unread, and the catch-all closes `userCards` again. The card `holder` fields stay, and the earlier schema ignores them.
- **Going live:** the DM enters the current hands with "+ Kart ver", as the owner decided.
